# Decision log

Short records of decisions and why. Newest at the bottom. Agents append here when they make a decision that affects more than one file or crate; to change an existing decision, add a new entry that supersedes it and explains why.

## D-001 Rust + macroquad (not SDL2, not Bevy)
- macroquad targets `wasm32-unknown-unknown` directly; SDL2 from Rust needs Emscripten for the web, which adds a C toolchain, bigger bundles and breakage.
- Bevy is powerful but heavy (compile times, ECS ceremony) for a 2D pixel game where we render in software anyway.
- Risk is contained: only `jnr-app` uses macroquad.

## D-002 Software renderer into a 320×180 framebuffer
- Pixel-perfect by construction, no GPU dependency (the container has none).
- The same code produces headless screenshots, so golden-image tests show exactly what the player sees.
- 320×180 is 16:9 and scales by whole numbers to 720p (×4), 1080p (×6) and 1440p (×8).

## D-003 Fixed-point simulation at fixed 60 Hz
- Bit-identical results native vs wasm → replays and solver bots stay valid everywhere.
- Classic platformers (SMB) use sub-pixel integer math too; it suits tight pixel-art movement.

## D-004 All assets as text sources
- `.sprite` text grids, procedural generators, ASCII levels, TOML text/tuning.
- Agents can author and diff them; no binary blobs in git except approved golden screenshots.
- Pixel art is produced inside the dev container with no external editor. **No LibreSprite / Aseprite** (human decision).

## D-005 Headless-first validation
- Every feature must be verifiable without a window (`cargo xtask verify`). The VNC window is for humans and a final smoke test only.

## D-006 Documentation in English, game text in German
- Docs, code, comments, commit messages: English.
- All player-visible text: German (Austrian flavour), only in `content/text/de.toml`.

## D-007 Fully autonomous agents (human, 2026-10-18)
- No human involvement: agents decide, commit, merge to `main` and accept milestones themselves (see `docs/milestones.md`).
- Web research and installing tools in the container are allowed; installed tools go into the dev container config.

## D-008 Game decisions (human, 2026-10-18)
- Title „Oblatenjagd"; hero **Resi** in a Dirndl; real names of places, businesses and historical people may be used; difficulty **medium** (see `game-design.md`).

## D-009 Parallel code tasks run in git worktrees
- Two engineers editing the same tree break each other's `cargo xtask check` (and block the orchestrator's Stop hook).
- Parallel code tasks therefore run in isolated git worktrees, each with its own `CARGO_TARGET_DIR` (`/workspaces/.cargo-target/wt-<task>`), and commit on their own branch; the orchestrator merges them into the milestone branch.

- (added in M1) The orchestrator deletes `/workspaces/.cargo-target/wt-<task>` when it merges or abandons that worktree; reviewers use one shared `wt-review` dir (deleted after each review). Each worktree target dir is 1–3 GB, and the 59 GB disk ran full once.

## D-010 Atlas data is owned and built once at startup
- The atlas types (`Atlas`, `AtlasSprite`, `AtlasAnim`) are plain owned data (`Vec`/`String`) shared by build time and runtime; `jnr_assets::atlas()` builds the atlas once via `OnceLock` from embedded RGBA bytes and generated metadata.
- One type family instead of separate `&'static` statics; the cost is one pixel copy at startup.

## D-011 Level semantics (jnr-core, M0)
- `.` is always empty air and can't be redefined in the legend; tile names map to collision kinds in core.
- Outside the grid: left/right are solid walls, solid tiles in row 0 extend upwards, below the level is empty and falling out kills.
- A goal is a pole covering its whole column above the goal cell, so it can't be jumped over.
- The player spawns grounded; `Dying` freezes the player; respawn resets the camera.
- No air drag; turning in the air uses `air_accel`. On the ground, speed above the current max (RUN released) decays by `friction`.
- (added after review) One-way platforms are dropped through only with DOWN + JUMP on the ground; DOWN alone does nothing (so walking over Zunftschilder while ducking is safe).
- The player hitbox size is a gameplay number in `content/tuning.toml`; sprite placement comes from the atlas origin, not from constants in core.

## D-012 Bitmap font convention
- Sprite `font` in `art/sprites/ui/font.sprite`, 8×8 cells, one anim `glyphs`; frame i = i-th char of `jnr_render::font::CHARSET` (89 glyphs: ASCII subset, ÄÖÜäöüß„“–…×%+). New glyphs are only ever appended, so indices stay stable.
- Glyphs are drawn in palette `w` only; the renderer tints them and draws the `k` shadow at (+1,+1).
- Advance = rightmost opaque column + 2; space (frame 0, intentionally empty, lint-exempt) advances 3 px; line height 9.

## D-013 Replay semantics and golden naming
- Replay frame numbers are `Game::frame()` values: frame N is the state after N steps, frame 0 the state before the first step. Shots and `frames=a..b` ranges (inclusive) use this numbering.
- A replay always runs all its inputs; end-state expectations (`state=`, `deaths`, `player_x>=`) are checked after the last input. Unknown expectation clauses are parse errors ("not supported yet"), so a replay never silently ignores a check.
- Replay parsing and expectation checks live in `jnr_core::replay` (pure, unit-tested); loading files, rendering and determinism runs live in xtask.
- Goldens are named after the replay, not the level: `tests/golden/<replay>_<shot>.png` (several replays may share a level). `golden --accept` re-renders instead of copying earlier actuals; rendering is deterministic, so the result equals the reviewed preview.
- `levels lint` runs in `check` (L3), not only in `verify`.
- (after review) A replay must have at least one expectation (runner failure, not a parse error); `replays` fails on an empty `tests/replays/`; goldens without a shot fail; goldens are only accepted from passing replays.
- The hand-written testbed route exists once, as `tests/replays/testbed_route.replay`; jnr-core's testbed test includes that file.

## D-014 Live smoke test and human recordings
- `vnc-smoke` plays `tests/replays/testbed_route.replay` in the real native window and requires its `--screenshot-at` framebuffers to be pixel-identical to the existing goldens (no separate VNC goldens). The X root screenshot is only checked for a sizable sky area (±8 per channel, the desktop is 16-bit RGB565), never compared exactly.
- `jnr-app --record` writes a replay with `source = human` and an `expect` line derived from the outcome (`complete frames=N..N` or `state=… player_x>=…`, plus `deaths=`), so every recording is a passing replay test the moment it is saved.
- Native Escape and window close end the session cleanly (macroquad `prevent_quit`) so the recording is always written; wasm keeps running until the page closes.

## D-015 Solver bot: search, jump window and solver replays
- The solver (`cargo xtask solve`, L4) is a frame-synchronous beam search over the real `Game` with a small fixed macro-action set; ranking is furthest right, then fewer jumps, then a stable insertion order, so the same level + tuning always gives the same route (threads only split work). The wall-clock limit is checked only while no completion has been found, so it can never change a route; but whether a search passes or fails can depend on machine speed if it runs into the limit, so the limit (60 s) is generous on purpose (the testbed takes ~0.6 s). jnr-core and xtask are built with `opt-level = 2` in the dev profile for speed.
- The jump window, the difficulty number level designers use (`game-design.md`: ≥ 6 frames in stages 1–3), is defined as: shift the whole held-JUMP segment by d ∈ [-12, +12], rest of the inputs unchanged; past the route's end the inputs are padded with the last input. Checkpoint = the first landing after the matching `Jumped` + 2 s; success = alive up to the next jump's checkpoint (or the end of the route) and at most 16 px behind the original at the own checkpoint (or finished). Window = contiguous successful shifts around 0, with the reason each side stopped: `fail` (the level), `route` (the shift would start before frame 0 or touch a neighbouring JUMP hold) or `max` (±12). Route-limited windows are only lower bounds and never count as the narrowest. It is measured on the cleaned route (no-op JUMP removed).
- Solver replays are `tests/replays/<level>_solver.replay`, written only with `--write`, and carry no `shots` by default (shots need art-director-approved goldens; `--shots` opts in).
- The `solver` verify step also requires the committed `tests/replays/<level>_solver.replay` for every level.
- A per-level `min_jump_window` waits for an optional `LevelMeta` field (backlog, M1); until then the `solver` step only reports the narrowest window.

## D-016 M0 movement tuning accepted unchanged (game-designer, M0 acceptance)
- The measured M0 movement (walk 1.5 / run 2.5 px/frame, jumps ~25 / 65 / 81 px, max fall 4 px/frame, coyote and buffer 6 frames, running jump ~9 tiles) is close to Super Mario Bros. and fits medium difficulty, so `content/tuning.toml` keeps its values in M1 (no replay or golden churn).
- The ~9-tile running jump is not "too far": it's a ceiling for optional routes. Required jumps in stages 1–3 follow the reach rules in `game-design.md` (gaps ≤ 4 tiles, step-ups ≤ 3; 5–6-tile gaps only with ≥ 8 tiles of run-up). The solver's ≥ 6-frame window stays the final check.
- New feel targets for M1 (new keys, not changes): walking jump reach ~5 tiles, stomp bounce ~1 tile (tap) / ~3 tiles (held), hurt invulnerability 120 frames.

## D-017 Stage 1 gameplay rules (game-designer, before M1)
- No ducking: DOWN is only used for one-way drop-through (D-011). Zuckerschock hitbox 12×30 px with the same physics; required passages are ≥ 2 tiles high.
- Stomp = falling and the feet above the enemy hitbox's middle on the previous frame. SMB-style stomp chain and scores (Oblate 200, power-up 1000, brick 50, time bonus 50/s). Maibaum scores by feet height in 2-tile zones up to 5000 for the Wurstkranz (≥ 8 tiles).
- The Fiaker can't be stomped, but landing on it bounces without damage (medium difficulty: no punishment for the obvious "jump on it" idea).
- A death resets the whole level (enemies, boxes, Oblaten) like SMB; checkpoint flag, score, Oblaten counter and lives survive; the timer is reset; the player is Normal again. Game over → „Weiter?" restarts from the stage start.
- Thrown Mozartkugeln are unwrapped chocolate balls, visually distinct from the wrapped power-up.
- Enemy patterns use frame counters from activation, never the RNG, so the solver and replays see fixed patterns.

## D-018 Level signs (game-designer, before M1)
- Signs are a decorative `sign` entity referencing a `de.toml` key, ≤ 2 lines of ≤ 12 characters each (`\n` separates the lines); this is how the skill's "signs ≤ 12 characters" applies to two-line boards. The level format for it (e.g. `{ entity = "sign", text = "stage.salzburg.sign_bus", style = "bus" }`) is the engine-engineer's choice.

## D-019 Input across respawn, replay limits, scene clamp
- While `Dying`, `Game::step` keeps updating `Player::jump_held` from the input, and `respawn` carries it into the new player. A JUMP held across a respawn is therefore not a new press (no auto-jump); presses during `Dying` never reach the jump buffer (it is not updated while dying and is reset on spawn).
- Replay files hold at most `MAX_FRAMES_PER_LINE` frames per input line and `MAX_TOTAL_FRAMES` in total (both 216 000 = 1 h at 60 Hz); larger files are parse errors with a line number, so a malformed replay cannot exhaust memory or run for ever.
- `cargo xtask scene` clamps the player's centre so its hitbox stays inside the level and prints a warning when it did; the camera clamps itself as before.

## D-020 Sprite catalog and autotiling (M1)
- `docs/sprite-catalog.md` is the contract between art and engine: sprite names, sizes, origins, animation names. The engine falls back to grey boxes for missing sprites, so art and code proceed in parallel.
- Autotiling without a new artkit header: a tile sprite with a 16-frame animation `auto` is drawn with frame = 4-neighbour mask (N=1, E=2, S=4, W=8; level edge counts as same). The `tileset` header stays unsupported.

## D-021 Parallax layers and procedural backgrounds (M1, engine)
- Background layers are `(sprite, factor in sixteenths)` pairs, back to front, set on the `RenderContext` (`with_background`); the level format provides the list later. Each layer is tiled horizontally from `-((camera.x * factor / 16) mod width)` and **bottom-aligned to the screen bottom**, with no vertical parallax for now (simple and predictable for art; revisit if levels scroll a lot vertically). Integer sixteenths keep the renderer free of floats.
- The flat sky fill stays behind the layers unless the first layer is fully opaque and at least screen-tall (precomputed once), so a partial layer list never shows stale framebuffer pixels.
- Generators live in `jnr-artkit::generators` (the requested `gen` name is a reserved keyword in Rust 2024) and turn `art/generators/*.toml` entries into ordinary `SpriteSource`s, so lints, compile, atlas and previews treat generated and hand-made sprites the same. Params are parsed with `serde` + `toml` (`Spanned` values give `file:line:col` errors); this makes `serde`/`toml` default dependencies of `jnr-artkit` (pure, wasm-safe, already used by `jnr-core`).
- Generated sprites are compiled into the game atlas like all art (the four Stage 1 layers add ~0.9 MB of raw RGBA to the embedded atlas).
- Autotile masks are computed from the live level while drawing (4 lookups per visible tile), not cached in the `RenderContext`, so tiles that change during play (bricks) stay correct; only the per-tile-name look is precomputed.

## D-022 Level format v2, entities, power states, level reset (M1, task E1)
- Legend values: a tile name, `{ tile = "...", contains = "oblate|mozartkugel|zaunerstollen|oblaten_10" }` (only `brick` and `oblaten_box`; a box defaults to `oblate`), or `{ entity = "..." }`; signs take `text = "<key>"` (required) and `style = "street|bus|ortsende"`. Unknown fields are errors. `[meta]`: `time_limit` is required (1..=999), `background = [{ sprite, factor, y }]` (factor in 1/16 of the camera speed, 0..=32; optional `y` = px above the screen bottom, 0..=180, default 0; orchestrator decision), optional `min_jump_window`. `RenderContext::for_level` wires it into `with_background(&[(sprite, factor, y)])`; the app, `replay --shots`/goldens, the solver images and `xtask scene` (unless `--bg` overrides it) use it.
- Level spawns are `SpawnKind` (level.rs); runtime entities are `entity::EntityKind` in one `Vec<Entity>` (enum + match, per-kind update). Level entities activate when their left edge is within `game.activate_margin` (320 px, one screen) of the right screen edge, and are removed `game.despawn_margin` px behind the camera or below the level. Order: spawns in grid order, then spawned entities appended.
- The current tile grid lives in `Game` (copy-on-write `Arc<TileMap>`), with a sorted list of changed cells for the hash; `Level` stays the start state. A death resets tiles, entities and the timer; score, Oblaten, lives and the checkpoint survive. Lives 0 → `Mode::GameOver`; START (after `game_over_frames`) restarts from the stage start with 3 lives, score 0, Oblaten 0.
- Power states: Normal/Big hitbox heights from tuning (feet stay in place), a 30-frame freeze for growing and shrinking (the whole game stands still, timer included), `invulnerable_frames` counted after the freeze (so 120 frames of play without harm). Hazards, pits and time-up kill regardless.
- Enemies are parsed and placed now as standing placeholders with the generic contact rules (stomp = falling and feet above the enemy's middle on the previous frame; otherwise hurt; Fiaker bounces only; SMB chain with the Verkäufer starting at 200), so hurt/stomp are testable; movement comes with the enemy task.
- (after review) Contact is order-independent: items and stomps are resolved for every touched entity first, hurts afterwards (one hurt per frame). Every enemy whose stomp rule holds in a frame is stomped (each counts in the chain); the player bounces once and gets **one `Stomped` event per frame**. The stomp rule uses the enemy's `prev_y` (snapshot before entities move) and the player's previous feet. `Entity` has per-kind `state: u8`, `dir: i8` (enemies start at -1), `base_y` for the enemy task; all hashed.
- (after review) At the lives cap an extra life does nothing: no `ExtraLife` event, no „+1 Leben" popup (points still count). Levels have at most 65 535 entity spawns (parse error). The Festungsbahn size is `platforms.festungsbahn_size` in tuning; frame counts where 0 breaks behaviour are validated ≥ 1.
- A head bump hits only the solid tile nearest the player's centre column. A brick with contents behaves like a box. Static Oblaten give no popup (SMB); everything else that scores shows one.
- `Game::world_hash` is a coarse progress hash (no timers, no cosmetic entities) used by the solver's de-duplication key; `state_hash` hashes everything exactly.
- Replay expectations `oblaten>=N` (HUD counter), `score>=N`, `lives=N`, `state=game_over`.
- Renderer: Zuckerschock uses `player_big` (fallback `player`) with the same anim selection; `PlayerAnim::Skid` (anim `skid`, fallback `walk`) while braking against the motion on the ground, drawn facing the direction of motion (sprite catalog), decided in the renderer so core's `facing` stays the input direction.

## D-023 QA rulings on items and stomping (orchestrator, M1)
- Stomp boundary stays as specified (D-017): a fall whose previous-frame feet are below the enemy's middle is a side hit, even near the corner. Generous enough for medium difficulty; revisit only if playtests disagree.
- Reaching 100 Oblaten shows the „+1 Leben" popup like the Zaunerstollen (unless at the lives cap).
- Goal and time-up in the same frame: the goal wins.
- Popups freeze during the 30-frame transformation freeze like everything else.

## D-024 Growing into a solid is a head bump (engine, M1 QA fixes)
- Growing keeps the feet (D-017). If the new Zuckerschock head then overlaps solid tiles (e.g. eating the Mozartkugel while rising just below a box), it counts as a head bump: upward speed stops and the hitbox is pushed down flush below the lowest overlapped solid tile (`Player::fit_head`). The block is not hit (no bump, no brick break).
- Tuning guarantees there is always room below: `hitbox_h_big` must not exceed `hitbox_h` rounded up to whole tiles (16 px), so every gap a Normal Resi fits in also fits Zuckerschock (validated in `tuning.rs`; 22 → 32 ≥ 30). Growing on the ground therefore never overlaps a ceiling.
- `TileMap::move_y` moving up never tunnels: a box whose top edge already is inside a solid row does not move up and reports `Ceiling`.
- Score popups: breaking a brick shows „50"; the 100th Oblate shows „+1 Leben" (D-023, none at the lives cap).

## D-025 Game flow, replay start, goal sequence (M1, task E4)
- `Game::new_at(level, tuning, seed, Start)`: `Start::Title` is the real game (the app's default): title screen → START → stage intro (`game.intro_frames` = 150) → play; after every death `Dying` → level reset + respawn → intro → play; game over → START (after `game_over_frames`) → intro; START during play pauses (`Mode::Paused`, nothing moves, timer stands still), START again resumes. `Start::Playing` (`Game::new`) starts in play and keeps the M0/E1 behaviour (no title, no intros, START does not pause; the goal sequence still ends in `Mode::Title`, and START there restarts the stage directly), so tests, the solver and all existing replays and goldens keep their frame numbers. JUMP is tracked in every non-play mode, so a held JUMP is never a new press afterwards.
- Replays opt into the real flow with the header `start = title` (default `playing`; written only when not the default). `--replay` uses the replay's `start`; `--record` writes the start it recorded with. New end states `state=title|stage_intro|paused`.
- Maibaum sequence (`Mode::StageClear` + `Game::stage_clear()`, phases `Slide → Hop → Walk → Tally → Clear → ToBeContinued`, then `Title` with the run reset to the stage start): at the first touch the height of the feet above the goal cell's bottom picks the zone (`goal.zone_heights` / `goal.zone_scores`; top zone = Wurstkranz + popup „Wurstkranz!"), the player is placed with her hitbox `goal.pole_offset` px left of the pole centre and slides at `goal.slide_speed`; at the base she is put `pole_offset` right of the pole and hops (`goal.hop_speed`, player gravity), then walks at walk speed with no collision until her hitbox is 16 px past the right screen edge (the camera stays); tally one second per frame (`score.time_bonus` each, skipped at 0 s); texts `goal.clear_frames` after the tally; „Fortsetzung folgt …" `goal.to_be_continued_frames`. Enemies, items and the timer freeze; popups, debris and bumps keep animating. Input is ignored (except JUMP tracking). Edge cases: a touch from the right side of the pole teleports her to its left side; a touch from below the base (feet lower than the goal cell's bottom) snaps her up to the base; the hop and the walk ignore terrain (no collision, a constant ground line at the base).
- Replay `complete` keeps its meaning (the frame of the first touch, `LevelComplete`); `state=stage_clear` holds for the whole sequence. The renderer shows `pole` while sliding; the stage-clear texts and the time-bonus line from the tally on.
- Stage text keys are `stage.<level id>.{title,tagline,next}`; when de.toml has no `stage.<id>.title` (test levels) the renderer uses `stage.salzburg.*` (M1 has one stage); `[meta].title_key` overrides the title.
- The Maibaum is drawn `goal.zone_heights[3]` (= Wurstkranz height, 128 px) tall: `maibaum_pole` tiles up from the goal cell's bottom, `maibaum_top` with its origin on the pole top. The old `goal` sprite name is gone.
- Pause (art-director ruling, art-style §11: no dimming, no dithering): the frozen level stays at full colour behind a palette panel, `B` fill at x 112–207, y 78–101, 1 px `k` border, 1 px `S` highlight on the top and left inner edges, `ui.pause` in `w` with the `k` shadow centred at y = 86.
- `Event::Respawned` comes only from the Dying path (a death → respawn); title → START and game over → START restart the stage without it.
- The HUD is drawn in `Playing`, `Paused`, `Dying` and `StageClear`, so every golden of a playing state shows it. With the `hud_oblate` icon the OBLATEN digits start at x = 106 (icon at x = 96).
- The title screen is static: its backdrop (background, tiles, Maibaum, Resi idle) and the logo are drawn at animation tick 0; only the START prompt blinks (y = 128).

## D-026 Enemy behaviours and the Festungsbahn (M1, task E3)
- Enemy patterns run on frame counters from activation (`Entity::timer`, per-kind `Entity::count`), never on the RNG (D-017). Distances to the player ("within 6/8/10 tiles") are horizontal, centre to centre. All numbers are `tuning.toml` `[enemies]` / `[platforms]` keys, validated in `Tuning::parse`.
- Selfie-Tourist: a selfie starts every `tourist_selfie_period` (240) frames counted from activation, so the first one is at frame 240 and it walks 192 frames between stops; the flash is frames 24–25 of the stop (renderer only, harmless). It turns at walls and at other enemies on foot (tourists, Verkäufer, parked Fiaker, a sitting Taube) by setting its direction away from the one it overlaps; it falls into hazards like into pits.
- Taube: integer sine via Bhaskara I's approximation (`enemies::sine_offset`, < 0.2 % error, exact at peaks and zeros, any period) around its start height, rising first; no table. The sitting Taube rises `taube_rise` px over `taube_rise_frames` from the frame the player comes close, then flies with the wave starting at its new height.
- Verkäufer: the throw counter only runs while the player is in range (it pauses outside, keeping a started wind-up pose until the player returns); the last `verkaeufer_windup` frames of each `verkaeufer_period` are the wind-up, the throw pose shows `verkaeufer_throw_pose` frames. The thrown Mozartkugel moves, then accelerates (apex 37.5 px with the design numbers, "~36"), passes through one-way tiles and vanishes on solid tiles or outside the level; it hurts on any contact and is never stomped.
- Fiaker: drives along its spawn row and **ignores tiles** while charging (it passes the Residenzbrunnen the design uses as a hiding spot; no gravity, so it never falls into pits); it is removed once its right edge is left of the screen. The generic top-contact bounce (no damage, no points) is unchanged.
- Bumping or breaking (Zuckerschock) a block knocks off enemies on it.
- Stomped enemies become `EntityKind::Defeated(kind)`: squished in place for `squish_frames` (Tauben tumble instead), no collision, left out of `world_hash`. Bumping a block knocks off stompable enemies standing on it (feet exactly on its top): `score.bump_enemy` (100, not part of the stomp chain), they tumble down off the screen; rolling items on it hop (`knock_speed`). The Fiaker can't be knocked.
- Festungsbahn: level syntax `{ entity = "festungsbahn", to = [dx, dy] }` (other end point in tiles relative to the spawn cell, required). Wait at the start, travel, wait, travel back; positions recomputed from the start point every frame. Only the top edge collides (from above); a standing player is carried by exactly the car's movement (with tile collision), so standing and walking on it are sub-pixel exact. Crush rule: the player is never crushed; a ceiling holds them and they drop through the car. Levels keep 3 tiles free above the car along the whole track (`levels lint`).
- The solver's beam keeps a "high" reserve (up to a quarter of the width: the highest node per 16 px column when higher than every kept one), because furthest-right ranking alone drops players waiting above a pit for the car (or riding it) in favour of nodes further right in the pit below. The testbed route is unchanged by it.
- Replays can assert `event=<Event>` (at least once).
- (merge with E1 QA / E4) Grey-box fixture: `{ entity = "selfie_tourist", still = true }` never walks or turns (`dir = 0`; selfie poses and contact rules unchanged). `00_items.level` uses it, so the E1/E4 regression replays built around a fixed target at column 34 (stomp boundaries, i-frames, 100-Oblaten loops, flow/goal goldens) stay valid unchanged. `levels lint` allows `still` only in `00_*.level` files, so real stages always have walking tourists.

## D-027 QA rulings on enemies, platforms and flow (orchestrator, M1)
- Trigger distances (sitting Taube, Fiaker, Verkäufer range) compare whole pixels with truncation; „within 6 tiles" means < 97 px. Accepted as specified.
- Enemy hit and goal touch in the same frame: the goal wins (consistent with D-023 goal vs time-up).
- A sitting Taube that rises and later hits a standing player is acceptable: the rise is the visible telegraph.
- Moving platforms never despawn. Every pit under a moving platform must have a way back up (stair-stepped rock as in the Stage 1 spec) — "falling off means waiting for the car or climbing back, never a softlock". A bounce off a non-stompable enemy (Fiaker) puts the player's feet on its top, so the bounce can never be followed by a side hit.

## D-028 Implementing D-027: Fiaker bounce, goal vs hit, pit recovery lint (engine, M1 QA fixes)
- Fiaker bounce: in a frame with a bounce off a non-stompable enemy, after the bounce speed is set, the player's feet are put on the top of the highest such enemy (`Game::rest_feet_on`). The move is upwards and shorter than the hitbox, so checking the new hitbox against solid tiles covers the whole way. If it would overlap a solid or hazard tile, she stays where she is and gets `enemies.bounce_grace_frames` (8, validated ≥ 2 since it counts down in the frame it is set) in which non-stompable enemies do no harm (`Player::bounce_grace`, hashed, counted down like `invulnerable`; every further bounce re-arms it). Stompable enemies, thrown Mozartkugeln and every other hurt are unaffected.
- Goal vs enemy hit: the hurt from `interact` is skipped when the player's hitbox overlaps a goal in that frame; the goal check later in the same step starts the Maibaum sequence. Hazards and pits still kill first (unchanged).
- Moving platforms (the Festungsbahn) are never removed by the despawn margin or the level bottom.

## D-033 Jump windows measure recoverability, not a fixed press chain (orchestrator, M1)
- Shifting one jump while keeping every later press fixed measured artefacts: a 1-frame shift could make a later fixed press miss its buffer, so the window collapsed although a player would simply press the next jump a frame later (Salzburg showed 1–2 frame windows that way).
- New rule: a shift d succeeds if the player survives the shifted jump AND a short re-planning beam search from the state right after the shifted jump's landing (small beam, horizon up to the next jump's checkpoint + margin) reaches at least the original progress at that checkpoint without dying. The window is still the contiguous range of successful shifts around 0 with `fail`/`route`/`max` bounds; `min_jump_window` keeps meaning "a human has at least N frames of slack for this jump".

## D-034 Implementing D-030/D-031 (engine, M1 task E5)
- Festungsbahn state machine (`platform::car`, `Entity::state` + `count`): `WAIT_LOWER` (count 0) → with a rider `UP` 1..=travel → `WAIT_UPPER` 1..=wait → `DOWN` 1..=travel → `WAIT_LOWER`. A rider = the player is grounded with feet exactly on the car's top and overlapping it, seen by the car's update after the player's own movement and landing (so the car leaves in the very frame she lands on it; JUMP pressed on the waiting car puts her in the air first, so it stays). An edge-only touch (her right edge on the car's left edge, or the reverse) is no overlap: it neither calls nor carries. A player standing on an adjacent tile whose top is exactly at the car's top height and who overlaps the car horizontally does call it (and is carried): accepted, since the car's top is 8 px off the tile grid at its ends, so this only happens with tiles placed along a moving car's path. The frame it arrives at the bottom it stops; a rider still on it takes it up again from the next frame. The lower end is the end with the larger y (`to` dy > 0: the spawn cell is the upper end, the car starts in `DOWN`); a level track's lower end is its spawn cell. Carrying, crush and landing rules are unchanged; positions are still recomputed from the spawn point each frame.
- Consequence: a player who fell into the pit after the car came down cannot call it while its lower end is behind the camera's left edge (the camera never scrolls back); the stairs required by the D-028 recovery lint are the way out. Not a softlock.
- Props are not core entities: `SpawnKind::Prop` spawns no `Entity`, has no collision and no hash; the renderer resolves them once (`RenderContext`) and draws them from the spawn list (front layer after tiles and before the Maibaum and entities; back layer after the parallax, before tiles; both also on the title backdrop). Missing sprite: the outline of the cell. `prop` takes `sprite` (required, checked by `levels lint` against `jnr_core::PROP_SPRITES`, which a test keeps equal to the prop rows of the catalog's „Props and goal" table, excluding the sprites of other entities: checkpoint, maibaum_*, sign_*, festungsbahn), `layer = "front|back"` and `dx` (px, ±64).
- Tiles: `facade`, `arch_under` and `invisible` are solid; `invisible` is never drawn (no sprite, no grey box) — it sits under props such as the Sphaera. Autotile families (`autotile_family` in `jnr-render/src/tiles.rs`, an explicit table): `arch_under` → `arch`, so the two count as the same neighbour in both directions.
- D-033 in the solver (`jump_windows`, `recovers`):
  - **Fast path:** the shifted inputs with the later presses unchanged reach the checkpoint progress (x − 16 px, or the finish) without dying. This is the old rule minus "survive up to the next jump's checkpoint".
  - **Otherwise, re-plan:** simulate up to the shifted jump's landing (died → fail, finished → ok; a press that made no jump is re-planned from the end of its buffer), then run a beam search with the solver's macros, beam `REPLAN_BEAM` = 12, from that state. It succeeds as soon as a node stands on the ground at x ≥ the goal (or finishes) by the checkpoint + `REPLAN_MARGIN` (30) frames.
  - **Horizon:** it is the jump's own checkpoint + margin, not the next jump's. Success is measured at that checkpoint, and the later route is re-planned anyway.
  - **Runtime:** the fast path covers most shifts. Debug-build `solve` wall time: testbed 1.6 s, items 1.4 s, enemies 3.4 s, Salzburg 27 s (its search is 7.5 s).
  - **Routes:** unchanged, because the window metric doesn't steer the search.
- `solver` verify step: fails when a level's narrowest jump window (route-limited windows excluded, as in the report) is below its `min_jump_window`, naming the jump frame and x (`solver::window_problem`).
- Addendum (engine, M2 tooling): **a recovery may take a small detour.** The re-planning search only has to reach the checkpoint progress standing on the ground; it may take another path there than the route, e.g. skip an Oblate or an item box the original jump collected, wait for an enemy, or take a different platform. The window measures "a human can still get on with the stage", not "the same score".
  - The fast path now also requires the player to stand on the ground at the checkpoint (like the re-planning goal), so a shifted run that passes the checkpoint x in mid-air (possibly into a pit) no longer counts by itself.
  - Each shift starts from a snapshot of the original route at its earliest changed frame (12 frames before the hold's first input) instead of frame 0; the jumps are measured in parallel (`jump_windows(…, threads)`, results in jump order, independent of the thread count) and `recovers` runs on one thread (its beam of 12 is too small to gain from threads). All four levels' windows are unchanged (Salzburg narrowest 7). Debug-build Salzburg `solve` wall time 25 s → 15 s (search 7.7 s).

## D-054 Climb camera, death line and vertical parallax (game-designer, M3 planning)
- Levels choose `[meta] camera = "side"` (default: today's camera, unchanged for every existing level, replay and golden) or `"climb"`. Horizontal behaviour is the same in both.
- **Climb, vertically (SMW style)**: while grounded (tile, one-way, platform, or crawling) the camera settles towards feet at screen y `climb_feet_y = 148` at ≤ `climb_settle_speed = 2` px/frame (148 = the street framing of Stages 1–3); in the air it follows up at once when the hitbox top rises above screen y `climb_top = 40`, and down while the feet are below 148, but never more than `climb_fall_follow = 80` px below the last ground's settle target. Reason: the dead-zone camera bobs with every jump in a tall level and after a climb leaves only ~3 tiles visible above Resi; settling on the ground keeps ~7.5 tiles above her visible, so upward jumps are never blind.
- **Death line**: in climb levels the player dies (as if falling out of the level) when her hitbox top is below the screen bottom. Together with the fall-follow limit: drops up to ~8 tiles survive, clefts ≥ 10 tiles kill within ~40 frames instead of a long fall to the level bottom. Levels never use drops of 7–9 tiles (survivable but off screen); `levels lint` checks this in climb levels (fall-depth lint: for every walkable edge, the drop into the open neighbouring column to the next standable surface must be ≤ 6 or ≥ 10 tiles, or bottomless).
- **Activation** in climb levels also needs vertical proximity (spawn cell within 64 px of the screen), so enemies far up the mountain don't wake up off screen and come down unseen. **Goal sequence** in climb levels settles on the feet at `climb_goal_feet_y = 164`, which frames the meadow like Stages 1–3 (D-029, D-040).
- **Vertical parallax**: background entries get an optional `factor_y` (sixteenths, 0..=32, default 0); the layer is drawn `(max camera y − camera.y) × factor_y / 16` px lower than today. At the level bottom nothing changes; layers only move down, so the sky never gaps. This supersedes D-021's "no vertical parallax for now" for layers that opt in.
- **Solver** in climb levels: furthest-right ranking can't see progress inside a vertical shaft. The beam ranks by `x + height gained` (px above the start's feet; deterministic, still integer), and D-033's recovery check also requires the feet to be no more than 8 px lower than the original at the checkpoint. If that proves hard, the engine may instead mark the shaft's jumps as route-limited and cover them with handwritten replays (then record it).
- **Fallback** (engine's call, record it if taken): a per-level dead zone (`camera_deadzone = [112, 136]`) with the existing follow, plus the death line and the activation rule. It bobs, but every design rule still holds.

## D-055 Climbing without ladders: jump-through planks and the shaft rule (game-designer, M3 planning)
- **No ladders.** Climbing is jumping: stairs and ledges (solid), and one-way wooden planks (`steig`) that Resi jumps up through from below, the classic SMB/SMW way up. Reasons: ladders need a new player state (grab, climb, UP/DOWN input, leaving the ladder, enemies and projectiles on ladders) with new animations in three power states, and they would make UP an action in one stage only. The real Falkensteinwand path is steep stairs and bolted wooden steps, not ladders, so planks are also the truthful picture.
- A missed jump through a plank lands on the plank or step it started from (missed jumps never fall more than 4 tiles onto safe ground).
- **Shaft rule**: a vertical section is at most **9 columns** wide inside its walls, entered at its bottom left and left at its top right, with nothing reachable outside its columns before the exit. Then the camera, which never scrolls left, can never strand a plank behind the screen's left edge (the rightmost possible centre puts the camera's left edge left of the shaft's first column). Planks overlap their neighbours by one column so walking enemies zigzag down plank by plank.

## D-056 The Hackl power-up (game-designer, M3 planning)
- **Obtained** from an `H`-Oblatenkiste (`contains = "hackl"`, boxes only). The item rises out of the box and stays put (no rolling, like SMB's fire flower). It turns **Normal or Zuckerschock** into **Hackl**; as Hackl it's 1000 points only. One per stage where it appears (Falkenstein: at the Hackelwurfkapelle, where the legend says Wolfgang threw his axe).
- **Hackl Resi is big** (12×30 hitbox, `player_hackl` 16×32, a green loden jacket over the dirndl), breaks bricks, and survives a hit by dropping to **Zuckerschock** (30-frame freeze, 120 i-frames). This is gentler than SMB1 (where fire → small) on purpose for medium difficulty. Every power change uses the same 30-frame freeze with alternating sprites. Death → Normal. **Carries over** into later stages like Zuckerschock (D-042); intro and route map draw `player_hackl`.
- **Throw = a new press of RUN** (SMB: B runs and fires). Holding RUN keeps running and throws only on the press. Max **2** axes alive; a press with 2 alive does nothing. No throws while frozen, crawling, dying or in the goal sequence. JUMP stays jump, START pause, DOWN drop-through / crawl.
- **Arc**: fixed and independent of Resi's speed: vx ±3.0 (faster than her run, so she never runs into it), vy −3.0, gravity 0.1875 px/frame², max fall 4.0. That is 1.5 tiles up and back at hand height after 6 tiles, ~7 tiles on flat ground. It sticks in solid tiles (20 frames, harmless), passes one-way tiles, vanishes in water/hazards and off screen.
- **Targets**: one per axe. Every stompable enemy is defeated for its base value (100/200, outside the stomp chain). The Fiaker is immune (it bounces off). Swarms and projectiles are passed through. A falling rock is shattered (50). Blocks and items are not affected (breaking bricks with the axe and cutting things are backlog).
- **Not taken**: a separate control for throwing (the game has four buttons and RUN is the SMB convention); a homing or straight axe (an arc is the legend's long throw and makes the axe skill-based); the axe also breaking bricks (it would trivialise box puzzles in every later stage).

## D-057 The Durchkriechstein: an optional scripted crawl (game-designer, M3 planning)
- D-011/D-017 "no ducking, DOWN only for drop-through" stays for movement. The one exception is that **DOWN at the mouth of a Durchkriechstein** (grounded on its floor, facing right, within 4 px of the mouth, JUMP not held, stone unused) starts a **scripted crawl**. Input is ignored while she moves right at 1 px/frame through the 1-tile-high tunnel (hitbox 12×12) and stands up at the exit. She can't be hurt, the timer runs, and she can't turn back (the custom: through in silence, without looking back).
- **Outcome**: Normal → +1 life (1000 points at the lives cap); Zuckerschock or Hackl → shed to Normal with the popup „Ballast weg!" (the legend: only the sinless fit, then even a large person does). Once per level attempt (a death resets it like a box), so lives can't be farmed: dying costs the life the stone gives.
- **Never a softlock**: the crawl is optional and always beside a required route over the boulder (≤ 3-tile step-up); walking into the mouth without DOWN just stops Resi at the boulder's face like a wall; the crawl is automatic, so any size fits; the exit has ≥ 2 rows of headroom and no enemy can reach it; `levels lint` checks the geometry (tunnel cells empty with solid above and below, the mouth's floor at the tunnel floor's height, 2 empty rows at the exit).
- **Not taken**: a 1-tile passage only Normal Resi fits through (her hitbox is 22 px, so it would need real ducking, and a big Resi would be blocked, which the custom contradicts); triggering by walking into the mouth (a big Resi would lose her power by accident on the main path); a forced crawl on the required route (it would punish carrying a power-up).
- **Fallback** (engine): if a visible crawl is costly, Resi may vanish at the mouth and reappear at the exit after the same number of frames (she's "inside the stone"); the `crawl` animations are then unused.

## D-058 Rules for the M3 enemies and hazards (game-designer, M3 planning)
- **Pilger**: like the Selfie-Tourist but without selfie stops: walks 0.5 towards the player, turns at walls and enemies on foot, **walks off ledges** (the climb's threat comes down the mountain). Groups are 2–3 pilgrims placed one cell apart; `lead = true` only swaps in the pennant-carrying sprite. 100 points.
- **Gams**: a ledge-bound hopper. Stand 60, crouch 16 (the telegraph), hop 32 frames (vx ±1.0, vy −4.0, gravity 0.25: 2 tiles up, 2 tiles across). At each crouch it faces the player and checks its landing cell: if there is no floor there at its height, or a wall is in the way, it turns; if both sides are blocked it hops in place. It never leaves its ledge. Stompable, 200 (chain start 200, D-046), knocked off by a bumped block.
- **Steinschlag**: a spawner in a cliff niche. Its counter runs only while the player is within `range` tiles (default 6) **and** the niche is fully on screen below the HUD, so every first rock of an approach shows the whole telegraph: 40 frames of wobble plus pebbles trickling down the column. Then a rock falls (gravity 0.25, max 4.0), shatters on the first solid or one-way tile, hurts on any contact (can't be stomped), passes through enemies and items. `period` 90–300 (default 150), `phase`. Level rules: niche bottom 4–6 tiles above the ground it hits; the stage's first rock drops onto a net; no rock column over the landing of a required jump that already has another hazard.
- **Rockfall net** (`netz`): an ordinary one-way tile. Rocks shatter on one-way tiles anyway, so a net 3 tiles above a path is a shelter and a platform with no new collision kind.
- All patterns are frame counters from activation or from entering range, never the RNG (D-017). The thrown Hackl's interactions with every enemy kind are in D-056.

## D-065 Climb camera: upward slack for the grounded settle (engine, M3 follow-up task E20)
- **Problem** (backlog "Falkenstein H-box framing", QA M3 acceptance): grounded, D-054's climb camera settles the feet at screen y 148, which shows only 32 px below them. Any box she can walk under has its top ≥ 3 tiles above the ground, so standing on it the ground she came from (and whatever walks there) leaves the screen. On the H-box (164, row 8; plateau row 11, axe lane row 12) the camera even rose to the level top and group C / the saddle Gams were thrown at blind.
- **Rule** (`Camera::follow_climb`, `ClimbFocus::settle_feet`): grounded, the camera settles towards the framing of the **settle feet** instead of the feet. They follow the ground down at once (any step down or level ground: settle feet = feet), but up only once the feet are more than `camera.climb_up_slack = 48` px (3 tiles) above them, and then only by the excess (SMB/SMW style). So a box or plank 3 tiles up keeps the framing, a 4-tile step settles 16 px, and in the shaft the first plank keeps the framing and every further one moves it by 3 tiles (grounded, the feet stay at screen y ≥ 100, so even a big hitbox top is ≥ 70 px down, well below `climb_top`).
- **Addition to the task's rule: `camera.climb_up_reach = 48`.** The slack holds only while she stays within 48 px (horizontally, hitbox centre) of where she stepped onto the ground she stands on (`ClimbFocus::slack_x`, reset on every new ground height); walking further, the settle feet catch up with her feet (at the usual 2 px/frame). Reason: without it any climb of small steps leaves the camera up to 3 tiles low **for good** (feet at screen y 100). On Falkenstein that silenced the Steinschlag: its spawners only count while the niche is on screen below the HUD (D-061), and after the Holzstiege or the trough the niches over path row 28 stayed above the screen, so rock #2 never fell in `qa_m3_hackl_vs_rock` (and 10 more QA routes broke through later Pilger wake-ups). With the reach every replay passes unchanged; the box tops, planks and the H-box (1 tile wide) are well inside it.
- **Unchanged**: in the air everything else is D-054 (the up-follow line while no slack holds, fall-follow limit, death line). The fall-follow limit is still measured from the **last ground's own** framing (`ground_feet`), not from the settle feet, so the death line and the fall-depth lint's 7–9-tile rule mean what they meant (a cleft beside a box kills exactly where it did). Start, respawn and stage changes frame the feet at 148 at once (settle feet = feet). The goal camera (D-059 addendum, E19) is unchanged. Side levels are bit-identical in play; their state hashes change only because the tuning (hashed via `Debug`) gained four keys (`climb_up_slack`, `climb_up_reach`, `climb_top_min`, `climb_catch_up_speed`) and `Game` hashes `settle_feet` and `slack_x` (both 0 there).
- **No bob on a held box (E20 review, option b; Normal still, big/Hackl a bounded ~8 px follow that settles back in ~4 frames).** With the slack holding, a jump from the box passed `climb_top`, the camera followed up and then settled back down: a bob on exactly the H-box spot. Now, in the air, the up-follow line is measured from the held framing: `climb_top − lag`, where `lag = settle_feet − ground_feet` (≥ 0, the framing's lag below the last ground's own), floored at `camera.climb_top_min = 11`. A Normal walk jump from a held 3-tile box peaks with the top at screen y 11 exactly, so it leaves `camera.y` unchanged; a run jump follows only as far as keeping the top at 11 needs (≥ the 8 px on screen the review asked for). The review asked for a floor of 8; **11 is the highest floor that still keeps the walk jump still**, and with 8 (or 9, 10) the re-solved Falkenstein route measured a narrowest window of **3** at the shaft's first plank jump (below `min_jump_window = 5`), with 11 it measures 8. Both values meet the review's "top at least 8 px on screen".
- **Landing catch-up.** In the shaft (planks 3 tiles apart) every plank after the first is held at the plank below, so a jump to the next plank no longer follows up and the landing leaves her top above `climb_top` (down to screen y ~13). The excess settle alone (2 px/frame) would leave her under the HUD for ~14 frames, a snap would pop the camera ~27 px: instead, grounded with the top above `climb_top`, the camera moves up `camera.climb_catch_up_speed = 6` px per frame more than the settle (8 in all) until the top is at `climb_top` (≤ 4 frames in the shaft). So grounded the top is above `climb_top` only during that catch-up, and never above `climb_top_min`.
- **Moving platforms**: on a vertically moving platform the feet change every frame, so every frame is "new ground" and `slack_x` resets every frame; the lag is still capped at `climb_up_slack` (riding up holds the framing until the excess, then follows). No climb level has moving platforms yet.
- **Tuning validation**: `0 ≤ climb_up_slack ≤ climb_feet_y − climb_top`, `climb_up_slack ≤ climb_fall_follow` (so a held framing is never below the fall-follow limit and the limit's "never pulls it up" can't hide a lower death line), `0 ≤ climb_up_reach ≤ 320`, `0 ≤ climb_top_min ≤ climb_top`, `0 ≤ climb_catch_up_speed ≤ 16`.
- **Falkenstein**: the solver route changed (vertical activation and the camera state steer the search): complete at **1540** (was 1542), 22 jumps, narrowest jump window **8** frames (frame 130, x 324; was 12). An intermediate cut of this task measured 6, and 3 with a floor of 8 (see above). D-064's "narrowest window 12" now reads 8. The tour re-copies the route; the other Falkenstein replays keep their copy of the M3 route (marked "before the E20 re-solve"). `falkenstein_rock_hit`: rock #2's niche comes on screen later on that route, the death moved 623 → 636 (shots re-picked 622/632).
- Tests (E20 review additions: `climb_up_follow_line_moves_up_by_the_slack_lag`, `climb_grounded_top_above_climb_top_catches_up_at_8_px_per_frame`, `a_walk_jump_from_a_held_box_leaves_the_camera_still`, `a_run_jump_from_a_held_box_follows_only_to_climb_top_min`, `falkenstein_h_box_top_keeps_the_axe_lane_on_screen` (the original bug: row 12 on screen for every frame she stands on the H-box in `falkenstein_hackl_axes`), the shaft test now checks the top ≥ `climb_top_min` in the air and ≥ `climb_top` from 4 frames after each landing): `camera.rs` (`climb_keeps_the_framing_on_a_step_up_of_up_to_3_tiles`, `climb_settles_up_only_by_the_excess_over_the_slack`, `climb_slack_holds_only_within_the_reach_of_the_step_up`, `climb_settles_down_at_once_below_the_settle_feet`, `climb_fall_follow_limit_is_measured_from_the_last_ground`), `tests/climb.rs` (`a_3_tile_step_up_keeps_the_ground_below_on_screen`, `a_4_tile_step_up_settles_by_16_px_at_2_px_per_frame`, `walking_on_along_higher_ground_settles_on_it`, `a_shaft_of_planks_3_tiles_apart_keeps_resi_on_screen`, `a_cleft_beside_a_box_still_kills_at_the_death_line`), tuning validation (see above). ## D-067 The Schafbergbahn: the Festungsbahn's state machine on a long 1:4 track (game-designer, M4 planning)
- New platform kind `schafbergbahn` (`to = [dx, dy]` required, 4 ≤ |dx| ≤ 32). It **waits for its rider** at the lower end, travels, waits `schafbergbahn_wait` = 90 frames at the top, travels back and waits again. This is exactly the Festungsbahn (D-030/D-034): landing, carrying, crush, never-despawn, positions recomputed from the spawn every frame. Its own numbers: body `schafbergbahn_size` = 64×32 (a whole number of tiles, so with whole-tile `to` both roofs lie on the tile grid and sit **flush with the station platforms**: walk on, walk off); travel = max(|dx|, |dy|) × `schafbergbahn_frames_per_tile` = 24 (Stage 5: 24 tiles = 576 frames ≈ 9.6 s; 0.67 px/frame across, so a hop on the roof drifts ~20 px back and lands on the 64 px roof).
- Reasons: a waiting train can't be missed, so a long ride over a lethal gorge is still a safe introduction; standing still is always safe. The Festungsbahn's fixed `festungsbahn_travel` (150 frames for any length) would be 2.6 px/frame on this track, faster than Resi runs. A free-running train (Gondel style) over a 10-tile gorge would turn a landmark into a timing test with long waits.
- The **renderer draws the track** (rails, rack, sleepers) from end to end + 1 tile, like the Gondel cable. It is the ride's telegraph and keeps the 1:4 slope out of the tile grid (no slopes, architecture.md). Steam puffs are renderer particles from the entity's counter.
- **Lints**: the 3-tile clearance applies to the train's **swept body**, so no solid or one-way tile may overlap the body anywhere along the track, nor the 3 tiles above its roof. The Festungsbahn lint only looked above the car; a 64×32 box moving up a 1:4 slope sweeps a parallelogram that stepped ground under the track could cut. The pit-recovery check is skipped over lethal pits, as for Gondel B (D-044). Level rule: no enemy, projectile or globe can reach the track or the rider while it can be ridden (D-032).
- **Fallbacks** (engine's call, record it if taken): (1) no drawn track: the level lays the decorative `zahnrad_gleis_0..3` tiles along the line instead; (2) if the new kind is costly, three `festungsbahn` cars of `to = [8, -2]` with 2-tile intermediate platforms (passing loops), drawn with the `schafbergbahn` sprite. This is the stepped fallback; its 150-frame travel is 0.85 px/frame, so it is fine. The gorge then sits under the middle car only.
- **Not taken**: real slopes (the architecture keeps AABB-on-grid collision); a train you ride to the summit (a stage of its own, backlog); jumps that inherit the platform's speed (no platform does; changing it would retune every moving-platform jump in Stages 1–2).
- **Addendum (engine, M4 task E21): as built.** Syntax and numbers as specified (`platforms.schafbergbahn_size = [64, 32]`, `schafbergbahn_frames_per_tile = 24`, `schafbergbahn_wait = 90`; validated: size 1..=64 px and whole tiles, frames per tile 1..=64, wait + 64 × frames per tile ≤ 32767). No fallback taken: the track is drawn. Deviations and findings:
  - **The roof follows the rail pixel for pixel** (pixel-artist request): the train's x is the straight line as for every platform, its height is snapped to whole px by `platform::rail_offset` (−floor(u · (−dy) / dx) from the spawn), so its 4:1 position never sits between two rail rows. Riders are carried by the train's own per-frame delta as before (exact); the end points are unchanged (whole tiles). The Festungsbahn and the Gondel keep the plain line (replays unchanged).
  - **Track look** (pixel-artist layout, art-director ruling): drawn behind the tiles; `d` rails at Y and Y+3, `m` rack at Y+1 (even columns) and Y+2, `O` sleepers 2 px wide every 8 px over Y+1..=Y+4 under the rails, a `d` girder at Y+5 **under the whole track** (one viaduct line, not a bare band like the Gondel cable), no light lip on the top rail (the diagonal must never read as a walkable slope); Y = the feet row at the spawn + `rail_offset`.   - **The swept-body lint is tighter than the stage text implies**: on a track rising right the body's lowest point over a column is where its lower right corner enters it, not its left edge: over column c (c ≥ body left column + 4) the bottom is B − 4 (c − c0 − 4) px on a 1:4 track. ## D-075 The auto-scroll camera (game-designer, M5 planning)
- Levels may choose `[meta] camera = "autoscroll"` with **`autoscroll = [from, to]`** (columns, required with this camera, a parse error otherwise; `0 ≤ from < to ≤ width − 20`). The zone is where the camera's left edge lies in `[from × 16, to × 16)`. Before it (**lead-in**) and after it (**lead-out**) the camera is the side camera, unchanged. Vertically it is always the side camera.
- **Scroll**: when following would put the camera at or past `from × 16`, it is set to exactly that and from then on moves right by `camera.autoscroll_speed = 192` subpx (**0.75 px/frame**) every frame of play (not frozen, paused, dying or in the goal sequence), independent of the player; the camera's x is the whole-px floor of the subpixel scroll position. At `to × 16` the side camera takes over (never left).
- **Push and squeeze** (SMB3 rule): in the scroll, after the camera and the platforms moved, a hitbox left of the camera's x is moved right by the difference with normal tile collision. If a solid tile stops that move, she dies (`DeathCause::Squeezed`, drawn as the normal hit death). **D-051 is off in the scroll**: a platform carrying her left past the edge pushes her across its deck instead of moving the camera. Outside the zone D-051 applies as before.
- **Right clamp**: in the scroll her hitbox's right edge stays ≤ camera x + 320 − `camera.autoscroll_right_margin = 64`; her movement and any carry stop there like at a wall. Without it she could outrun the screen. With 64 px, she always sees ≥ 4 tiles ahead and anything entering the screen is ≥ 64 px from her.
- **Start, respawn, goal**: framed as in side levels. If the framing lies inside the zone, the scroll resumes after `camera.autoscroll_hold = 60` frames of play (a calm respawn on a checkpoint in the zone); the lead-in → scroll transition never holds. The goal column must be ≥ `to + 20` (lint), so the goal sequence always uses the side camera.
- **Visibility rule for enemies in a scroll zone**: triggers that start a threat also need the enemy **fully on screen** (the swan's and the regatta boat's triggers, the Gelse's wait counter), so with the right clamp every threat is in view ≥ 60 frames before it can touch her. Activation is unchanged (one screen ahead). In the scroll, the camera doesn't depend on the player, so activations happen at fixed scroll positions and boat phases can be tuned exactly.
- **Lints** (`levels lint`): goal ≥ `to + 20`; **squeeze faces**: every left-facing solid face in the zone's columns has its top ≤ 3 tiles above the surface in front of it (deck, water surface or lake bed), so the edge can always push her onto it; the checkpoint in a zone stands on a deck tile (solid or one-way), not on water.
- **Solver**: its frame budget covers the scroll (zone length in px / speed, plus the usual budget for the rest); `world_hash` covers the scroll phase, position and hold. Fallback (as D-054's): if the beam can't hold a route through the zone, the zone's jumps are marked route-limited and covered by handwritten replays (record it).
- **Tuning validation**: `0 < autoscroll_speed < swim.speed`, hold 0..=600, margin 0..=160, and the Dampfer at least as fast as the scroll (D-077).
- **Reasons**: a lake crossing has a pace of its own, and a scroll makes the boats' timing a timeline the designer controls, where the side camera would leave it to the player's dawdling. Pushing instead of killing at the edge (SMB3) is forgiving, and the squeeze death only exists where a wall is. Stage 6 designs every wall out (no solid tiles on rows 11–12 over water), so the rule is there for correctness and later stages. 0.75 px/frame is half the walk speed and 0.5 px/frame slower than swimming, so every way of moving can gain on the edge. Keeping the zone off the start and the goal leaves the intro screen, the goal sequence and the D-029 framing untouched.
- **Fallback** (engine's call, record it): ship the stage as `camera = "side"`. The level is built left to right and stays fair; boats and enemies then wake by the player's progress, and push, squeeze, clamp and hold go unused.
- **Not taken**: a scroll that also moves vertically (not needed on a lake); a scroll speed set per level (one tuning value is enough for one stage; a per-level override can come when a second auto-scroll stage needs it); killing at the left edge without a wall (harsher than SMB3 for no gain); a zone covering the whole level (the start would push Resi before she has seen anything, and the goal camera would need new rules).

## D-076 Swimming (game-designer, M5 planning)
- **Swim water is a new tile kind** (`TileKind::Swim`; tiles `see_wasser` = surface look, `see_wasser_tief` = deep, `steg_pfahl` = water with a pier post). The existing water tiles stay lethal (D-050), so Stages 1–5 are unchanged, and future stages can mix both. Swim water is drawn clear, with the lake bed showing through (the real lake's 8 m visibility), and Stage 6 teaches it on its first screen (sign „Baden heute / erlaubt", a bathing notch with Oblaten under water). **Not taken**: a level-wide "water is swimmable" flag (it would silently change what an existing tile means, and a level could never have both).
- **Swimming** = her chest point (hitbox centre x, 8 px below her hitbox top, every form) is in a Swim tile. **At the surface** = within 8 px below a swim surface (a Swim tile with no Swim above). She can't swim her chest above the surface; only a jump-out leaves upwards.
- **Physics** (tuning `[swim]`): floating at the surface (no gravity) unless DOWN is held; otherwise gravity 16 (0.0625 px/frame²), max sink 256 (1.0); a new JUMP press below the surface band strokes (vy −448, ~24 px up, `Event::Stroke`); a new JUMP press at the surface is a **jump-out** with `jump_speed_walk` (`Event::Jumped`, normal airborne rules after it); horizontal accel 16, decel 8, max 320 (1.25 px/frame, RUN no faster); on entering, vy is clamped to [−stroke, max sink] and the jump buffer and coyote are cleared. The lake bed is ground (walk at swim speed, JUMP strokes). No breath meter.
- **DOWN gets a third meaning** (after drop-through, D-011, and the crawl, D-057): held at the surface, it lets Resi sink. Reason: floating at the surface keeps a relaxed swimmer from having to tap, which SMB's always-sinking swim demands; diving then needs one intentional input, and DOWN = down is the obvious one. Under water DOWN does nothing more (no dive boost: one gravity value is easier to read and to test).
- **While swimming**: every enemy contact hurts (no stomps, no roof bounces; a jump-out is airborne from its next frame and can stomp); RUN throws no Hackl; axes and power-up items touching swim water are removed or lost as in water. Walking enemies treat Swim like Water. Entity-on-tile (D-049) is extended to Swim tiles, so Oblaten, swans and regatta boats can be placed in water cells.
- **Same numbers in every form** (only the hitbox height differs). A held jump-out reaches a deck 1 tile above the water in every form (Normal feet ~53 px above the surface, big ~45 px); a tap doesn't. That is the level rule "decks 1 tile up" and a feel test.
- **The solver's window metric** counts `Jumped` (incl. jump-outs) and never `Stroke`.
- **Lint**: every swim column ends on a solid tile inside the level; in a scroll zone, no solid tile sits directly on a swim surface.
- **Reasons**: SMB's water levels are the reference (sink, stroke, slow horizontal movement), with two changes for a lake you swim on more than in: the surface holds her, and a jump-out from the surface is a normal jump, so boats are boarded with the same skill as a jump onto a ledge. The dive is the answer to the stage's surface and air enemies (swans, regatta boats, Gelsen), which gives swimming a purpose beyond "not dying".
- **Fallback** (engine's call, record it): **surface-only swimming**. The chest point is held at the surface (no sinking, no strokes, DOWN unused), and JUMP is the jump-out. The level then gives every swan a deck within its charge range and every regatta lane a Traundl, since diving is gone. Lethal water and all other rules stay.

### D-076 addendum: swimming as built (engine, M5 task E27)
- **Full swimming, the fallback (surface-only) is not taken**: every rule of D-076 is implemented with the designer's numbers (`[swim]`: `chest_px` 8, `surface_band` 8, `gravity` 16, `max_sink` 256, `stroke_speed` 448, `accel` 16, `decel` 8, `speed` 320), measured by the feel tests (stroke rise 23.6 px, max sink 1.0, 12 px of sinking in 20 frames, 1.25 px/frame with and without RUN, a held jump-out lands on a 1-tile deck or quay in every form and a tap doesn't; jump-out feet heights Normal 53/11 px, big 45/3 px within ±4).
- **Engine choices the spec left open**: (1) Swimming is decided once per step from the position before the move (`Player::swimming`); the rise cap then holds the chest at the surface line after the move. (2) A jump-out sets `Player::leaving_water`: until she stops rising she follows the normal airborne rules even while her chest is still in the water (otherwise the cap would catch the jump-out in its first frames); this is what "airborne from its next frame" means in code. (3) Floating keeps the depth at which she stopped (vy 0 anywhere in the band, no snap to the line); falling in, the entry clamp and the float rule stop her on her first swimming step unless DOWN is held. A stroke from below ends exactly on the line. (4) A new press on the very step that enters the water is a real press (a jump-out at the surface); only presses buffered before it are dropped. (5) In swim water the coyote frames stay 0, also on the bed. (6) The surface over the chest is the top of the run of swim tiles it is in, so under a solid tile (a box in the water) that tile's underside counts as the surface; the zone lint keeps solids off swim surfaces where it matters.
- **What is lost in swim water** (D-076 "as in water"): items, thrown axes, E-Bikers and snow globes via `TileMap::swallows` (Hazard, Water, Swim; `touches_lethal`, still Hazard and Water, only guards the roof-bounce placement, since swim water is no danger to Resi). Walking enemies would sink out of the level in lethal water but meet a lake bed here, so they are **removed at the touch** of a swim tile (`EnemyKind::sinks_in_swim_water`, an exhaustive match: the M5 kinds of E29 must classify themselves; the Taube, the Bienenschwarm and the tile-ignoring Fiaker and Reisebus don't sink).
- **Unchanged**: lethal water (D-050 tests pass unchanged), every earlier replay, solver replay and golden. State hashes change only because the tuning gained `[swim]` and the player three hashed fields (`swimming`, `leaving_water`, `swim_frames`); the testbed's pinned finish hash was re-pinned (route and frame unchanged).
- **Solver**: the window metric skips a JUMP hold whose press swims a `Stroke`; jump-outs count like jumps. Its search and recovery need nothing new for the grey box `00_m5_swim`; the scroll zone over swim water is E30's.
- **Integration with E25/E26/E28/E29** (merge of `m5-wolfgangsee`): `Tuning::validate_swim` now also requires `camera.autoscroll_speed < swim.speed`; `levels lint` passes `swim::problems` the columns the scroll shows (`from` to `to − 1 + 20`, the camera's left edge lying in `[from × 16, to × 16)`). The Schwan, the Gelse and the Regattaboot don't sink in swim water. `steg_pfahl`'s art is an `auto` 16-frame autotile on its own name (N: pile above, S: pile below; its frames ignore E/W), so no autotile family rule was needed (render test). Left for E30: the contact rule while swimming goes through E29's `enemies::contact(kind, from_above, swimming)`, fed by the `Game::player_swimming()` stub (still `false`); the two contact tests (`every_enemy_contact_hurts_while_swimming`, `no_roof_bounce_while_swimming`) are `#[ignore]`d until it returns `Player::swimming`, as are the `// E27: | Swim` markers of E28/E29.

## D-082 Verify runs independent work in parallel; the solver runs over the real levels only in `verify` (engine-engineer, E25)
- **Context**: `cargo xtask verify` had grown to ~7.5–8.5 min against the 10-min budget (test step ~5 min, solver ~2.3 min) and grew ~1 min per stage. Most of the test step was one test, `verify_fails_without_the_committed_solver_replay`, which solved every real level twice inside `cargo test` but accepted any result, so it never checked that a level is solvable.
- **Decision**: (1) that test checks the `solver` step's bookkeeping (missing replay, level order, a stuck level) on synthetic levels; the `solver` verify step alone solves the real levels, as before. (2) Independent items run on scoped threads with results joined in item order (`xtask/src/par.rs`), so reports are identical for any thread count: the replays (`replays` step and its test; both determinism runs of a replay stay on one thread), the golden shots, and the solver's levels. (3) The `solver` step runs in two passes. Pass 1: every level's search, the only part with a wall-clock limit, largest level first, never more busy threads than cores: about 7 threads per level, at most 8 (14 cores: 2 levels at a time × 7). Pass 2, after all searches: route clean-up and jump windows (no clock) for every level at once on all cores, then the reports in level order. (4) Solver test output goes to per-process folders (`tmp/xtask-solver-test/<pid>/`), so a `check` and a `verify` at the same time no longer delete each other's files.
- **Measured** (14 cores, warm build): `verify` 500 s → 93–141 s depending on other agents' load (test 320 s cold / ~5 min warm → 10–15 s; solver 136 s → 60–105 s). The slowest search is 16.5–18.2 s (two runs) at a load average of 20–35, ≥ 3.3× below the 60 s limit; 4 levels × 3 threads with the windows overlapping other levels' searches had given 21–25 s. All 17 solved routes equal the committed solver replays.
- **Not taken**: caching solver results by content hash (the key would have to cover the level, the tuning and all code, e.g. by hashing the xtask binary; not needed at this runtime, kept in `backlog.md`); `opt-level = 3` for jnr-core/xtask (no gain); one thread per level for all levels at once (133 s: the large stages become the critical path).

## D-083 Implementing D-075: the auto-scroll camera (engine, M5 task E26)
- **Format**: `CameraMode::Autoscroll` and `[meta] autoscroll = [from, to]` (`LevelMeta::autoscroll`, `autoscroll_zone()`); `Level::parse` rejects a missing zone, a zone with another camera, and anything but `0 ≤ from < to ≤ width − 20` (`level::SCREEN_COLS`).
- **Camera** (`camera.rs`): `Autoscroll { phase: ScrollPhase, pos, hold }` in `Game` (`Game::autoscroll()`), `Camera::follow_autoscroll` as D-075's table; start, respawn and stage changes frame as in side levels and `Autoscroll::placed` sets the phase from that framing (inside the zone: `hold = autoscroll_hold`). The hold and the scroll advance only in `follow_camera`, which frozen, paused, dying and goal-sequence frames never reach. **Lead-out is final**: "never left" is read as "never back to the scroll"; D-051 still applies in the lead-out (a rider carried left there moves the camera left as in any side level, the phase stays `LeadOut`). Stage 6 has no platform at the zone's end, so this never shows.
- **Order in a frame** (scroll only, `Game::scrolling`, the hold included): the player's own movement and every carry use the clamp from the frame's starting camera (`player::Bounds { min_x, max_x, max_x_speed }`, `platform::carry(.., max_x, ..)`); D-051 (`follow_carried_left`) is skipped; after the checkpoint, goal and camera follow (also on the frame the scroll hands over to the lead-out), `push_from_left_edge` moves a hitbox left of the new camera x right with `TileMap::move_x` (only solid tiles block), and if it ends short of the edge she dies with **`DeathCause::Squeezed`** (state-hash tag 5, rendered like `Hit`).
- **Addition: the right clamp keeps pace.** "Stops there like at a wall" taken literally (speed set to 0) made a runner at the clamp stutter: the clamp moves 0 or 1 px a frame, she lost her speed at every touch and fell up to 3.4 px behind in a 16-frame saw-tooth (measured on the grey box). Stopped at the clamp her speed is now capped at `autoscroll_speed` instead (0 during the hold), so holding right she stays < 1 px behind it (`the_right_clamp_stops_her_own_movement`). The clamp never pulls her left (if she were ever past it, she just can't move further right). The carry's clamp only stops the carry; her speed is untouched. For the level-designer: as at a real wall, a jump from the clamp is therefore a walking jump (`jump_speed_walk`), so gaps and hops a rider at the clamp must take need walking-jump reach.
- **Hashes**: `state_hash` and `world_hash` include the scroll state only in auto-scroll levels, so every other level's search and hashes stay as they were; the three new tuning keys are in the static hash (tuning `Debug`), so the testbed's pinned `FINISH_HASH` changed (frame unchanged). Every earlier replay, solver replay and golden passes unchanged.
- **Tuning** `[camera]`: `autoscroll_speed = 192`, `autoscroll_hold = 60`, `autoscroll_right_margin = 64`; validated `0 < speed < player.walk_speed` (interim stand-in for D-075's `< swim.speed`, which E27 adds with `[swim]`; the Dampfer check is E28's), hold 0..=600, margin 0..=160.
- **"Fully on screen"**: `Camera::fully_on_screen(&Aabb)` (pub) and `UpdateCtx::fully_on_screen(&Aabb)` (pub(crate), for entity updates; E29's swan, Gelse and regatta triggers use it through `enemies::fully_on_screen`): the hitbox inside the camera rectangle, its edges included.
- **Lints** (`xtask/src/scrolllint.rs`): goal ≥ `to + 20`; squeeze faces in the columns seen during the scroll (`from .. to + 20`) with a **pass-under** reading: a face with ≥ 2 empty rows between its bottom and the surface in front (Resi's tallest hitbox is 30 px) is overhead and skipped, otherwise its top must be ≤ 3 tiles above that surface (for water: the water body's top). Without it the stage's own rule "boxes/bricks ≥ 4 tiles above a deck" would fail the lint. Known gaps for E27/E30: a one-way deck over water is "the surface" for a face behind it, so a swimmer under the deck is not checked against that face (Stage 6 keeps rows 11–12 over water free of solids, so it can't happen there); faces in columns `to + 1 .. to + 20` are checked although the edge never reaches them (stricter than needed). ## D-084 M5 integration: squeeze faces over swim water, the solver over water, the cross-task stubs (engine, M5 task E30)
- **Squeeze faces over swim water: at most 2 tiles** (`levels lint`, code-review finding on E26/E27). D-075's limit of 3 tiles assumed she stands on the surface in front of the face; a swimmer climbs out with a held jump-out instead, and the weakest form's reaches only ~45 px (big and Hackl Resi; Normal ~53). So a left-facing solid face in an auto-scroll zone whose surface in front is a **swim** surface may rise at most `jnr_core::swim::MAX_FACE_TILES` = 2 tiles above it (32 px); over a deck, the ground or lethal water the limit stays 3. The number is not hand-waved: the feel test `jump_out_heights_bound_the_squeeze_face_over_swim` measures every form's held jump-out from the water line and fails if the weakest one doesn't clear 2 tiles, or would clear 3 (then the limit should rise). **Not taken**: deriving the limit at lint time from a simulation (the lint would depend on the player physics at run time; the test pins the same thing).
- **Pit recovery under boats (D-077) skips swim water only.** E28 skipped every column whose first tile below the track is `Water` as a stand-in for swim water. With swim water real, the narrowest rule that keeps every existing level lint-clean: columns over **swim** water are skipped (a fall is a swim) and an exit over swim water passes; **lethal** water is looked through again as before D-077 (a fall into it is a death, not a softlock, and the floor below it counts). Every level in `content/levels` lints clean under it; the unit test `boats_skip_the_pit_recovery_over_water` covers swim, lethal and dry basins.
- **Solver jump windows over water (D-033).** A window's checkpoint is the first landing + 2 s; over water the route is often in the air or swimming there, and "standing at the route's x minus one tile" can then be impossible for any run, the original included (`00_m5_swim`: the bollard hop measured 1 frame because the route was in the air over open water at its checkpoint). A shifted jump that ends in swim water hands over to the re-planning at its first swimming step (E27), and the recovery still has to stand on the ground: a surface swimmer never counts as recovered (the lake bed is ground), and no extra time is granted (an extra 2 s for swims was tried and made no difference on the grey boxes, so it was dropped as loose). `00_m5_swim`: narrowest 25 (was 1).
