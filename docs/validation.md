# Validation: closing the agentic loop

Status: **approved v1**.

Goal: an agent can implement a feature and **prove** it works without a human looking at it. The project runs with **no human involvement**; milestones are accepted by the agents themselves (see `milestones.md`).

## Two entry points

| Command | When | Target time |
|---|---|---|
| `cargo xtask check` | after every change, enforced by a hook before an agent may finish its turn | < 60 s incremental |
| `cargo xtask verify` | before every commit / task completion | < 10 min |

Both write a machine-readable report to `$CARGO_TARGET_DIR/reports/{check,verify}.json` (here: `/workspaces/.cargo-target/reports/`) plus a short Markdown summary that agents read. Every failure includes the exact command to reproduce it.

**Runtime** (E35, D-091; 14-core dev container, warm build, 23 levels incl. Stage 6): `verify` ~2.7 min with a cold solver cache (test ~25 s, solver ~95–110 s: searches ~40 s + jump windows ~55 s, replays ~2 s, goldens ~1 s, wasm-smoke ~6–10 s, vnc-smoke ~13–15 s) and ~50 s when every level comes from the solver cache (solver ~2 s); Stage 6 had pushed it to ~5.3 min (solver ~270 s) before E35; before E25 ~7.5–8.5 min. Timings rise with other agents' load. Independent items run in parallel on scoped threads with results joined in item order (`xtask/src/par.rs`), so every report is identical for any thread count: the replays (`replays` step and the `real_replays_pass_and_render_shots` test), the golden shots, and the solver's levels (searches first, then jump windows; see the `solver` step). `cargo test` no longer runs the whole solver over every real level: `verify_fails_without_the_committed_solver_replay` used to solve all levels twice (~4.5 min of the test step) without asserting that they were solvable; it now checks the step's bookkeeping on synthetic levels, and the `solver` verify step alone solves the real levels (as before). Solver test output goes to `$CARGO_TARGET_DIR/tmp/xtask-solver-test/<pid>/` (per process, so a `check` and a `verify` running at the same time no longer delete each other's files; directories of finished processes are removed by the next run).

## Layers

### L1 Static (check)
- `cargo fmt --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- Native build + `cargo build -p jnr-app -p jnr-audio --target wasm32-unknown-unknown`
- **Architecture lint**: `jnr-core`, `jnr-render` and `jnr-audio` must not depend on macroquad (`jnr-audio` also not on quad-snd or rand; only on `jnr-core` in the workspace; `jnr-render` not on `jnr-audio`); no `f32`/`f64` in `jnr-core` or `jnr-audio` (except in tests); no `HashMap` there; no `std::time`/`std::fs` there; tooling-only functions (`Game::teleport_player`) are called only from xtask and tests. Implemented as a simple dependency-tree + grep check in xtask.

### L2 Unit tests (check)
- `cargo test --workspace`: physics, collision, entity behaviour, level parsing, sprite parsing.
- **Game-feel tests**: simulate the player with scripted inputs and assert the targets in `game-design.md` (e.g. "holding JUMP while running reaches 5 ± 0.25 tiles", "coyote jump works 6 frames after the edge").

- `cargo xtask audio lint [id]` (step `audio-lint`, E56): every sound in `audio/sfx/` and `audio/jingles/` is rendered and checked against its entry in `audio/targets.toml` (see "Audio (L3 + L6)" below).

### L4 Level completability (verify)
- **Solver bot** (`cargo xtask solve <level>`): a beam search over the real `jnr-core` simulation. It clones `Game`, tries macro-actions (e.g. run right 8 frames, run+jump held N frames, wait), keeps the most promising states (furthest right, alive, highest score) and stops when `LevelComplete` happens.
- Output: a replay file that proves the level can be finished. A level the bot can't finish fails verification, with a report of the furthest point reached and a screenshot there.
- The bot also reports **difficulty signals**: number of frames, how narrow the successful jumps were (frame windows), and deaths during the search. These go into the level report for the `level-designer`.
- Implemented (M0, `xtask/src/solver.rs`, D-015):
  - **Search**: frame-synchronous beam search (default width 64): nodes are bucketed by frame and buckets processed in frame order; each bucket is ranked (furthest right, then fewer jumps, then insertion order), de-duplicated by a coarse state key (x/y in 4 px cells, vx in 1/4 px, vy in 1/2 px, grounded, plus `Game::world_hash`: changed tiles, gameplay entities in 4 px cells, for enemies, projectiles and the Festungsbahn also activation, state, facing and pattern counter, checkpoint, power state, and the stage clock while an Offizier is in the entity list (E41, D-099)), cut to the beam width plus a reserve that keeps at least a quarter of the beam grounded and a "high" reserve (up to a quarter of the beam: a node whose feet are higher than every kept node's in its 16 px column, so a player waiting above a pit for the Festungsbahn, or riding it, survives against nodes further right down in the pit), and expanded with every macro-action. Macro-actions that die are pruned and counted as **search deaths**; touching the goal stops the macro. The first completion (earliest frame, then fewest jumps) wins. Fails when every branch dies, after the frame budget (3× level width in px) or the wall-clock limit (default 60 s, `--time-limit`). The route is deterministic: it does not depend on the thread count, and the clock is checked only while no completion has been found. Pass/fail can depend on machine speed if a search hits the limit, so the limit is generous (testbed: ~0.6 s with `opt-level = 2` for jnr-core and xtask in the dev profile).
  - **Action set**: `RB 4/8/16`, `R 8`, `- 4/16`, `L 4`, `LB 8`; running jump `RBJ k` (k = 1, 6, 12, 20, 36) + `RB 2`; walking jump `RJ k` (k = 1, 12, 36) + `R 2`; `LBJ 12/36` + `LB 2`; drop-through `DJ 1` + `- 3`.
  - **Route clean-up**: JUMP holds are removed or shortened where the player's position stays identical on every frame (mid-air presses, holds past the apex).
  - **Jump window**: for each JUMP press that makes the player jump, the whole held-JUMP segment is shifted by d ∈ [-12, +12] with the rest of the inputs unchanged (padded with the last input past the route's end). Checkpoint = first landing after the matching `Jumped` + 120 frames, capped at the finish. A shift succeeds (D-033) if the player survives the shifted jump and then reaches the original x at that checkpoint minus 16 px (or finishes) without dying. Either the unchanged later inputs get there by the checkpoint, standing on the ground (fast path), or a re-planning beam search (`solver::recovers`: the solver's macros, beam 12) does: it starts right after the shifted jump's landing (or after the jump buffer ran out if the press made no jump), and a node must stand on the ground at that x by the checkpoint + 30 frames. The window is the contiguous successful range around d = 0 (max 25). Each side records why it stopped: `fail` (a shift failed: the level's limit), `route` (the shift would start before frame 0 or touch a neighbouring JUMP hold) or `max`. Windows with a `route` side are lower bounds (`≥` in the report) and never count as the narrowest. A recovery may take a small detour (skip an item, take another platform; D-034). Each shift starts from a snapshot of the original route 12 frames before the hold's first input (the earliest frame a shift changes). Every shift of every jump (in `verify`: of every level) is one item of a shared work queue on all cores, smallest |d| first; a shift beyond an already failed one on the same side is skipped, and each window is grown from the results exactly as shift after shift, so the windows do not depend on the thread count (E35, D-091: before, one jump's shifts ran one after the other, and Wolfgangsee's jump at frame 1325, 24 re-plans of ~2900 frames each across the lake, took ~200 s alone).
  - **Solver cache** (E35, D-091; `xtask/src/solver/cache.rs`): a complete solve (route, search numbers, windows) is stored in `$CARGO_TARGET_DIR/cache/solver/<level>.json` under a key over everything that decides it: the parsed level and tuning (`Debug` text), beam width, frame budget and time limit, and `XTASK_SOLVER_CODE_HASH`, which `xtask/build.rs` hashes at build time over every file of `crates/jnr-core` and `xtask`, `Cargo.lock`, the workspace `Cargo.toml`, `rustc -vV` and the build profile (so the hash always describes the compiled code; art, render and app changes don't invalidate it). `solve` and the `verify` step reuse an entry whose key matches instead of searching and measuring again; the reports, images and checks (window minimum, committed replay) still run, and the output says `from the solver cache`. Failed searches are never stored. `cargo xtask solve … --no-cache` and `cargo xtask verify --no-cache` solve everything (and overwrite the entries); a fresh target directory (CI) has no cache.
  - **Speed** (E35, D-091; routes and windows unchanged, checked against every committed solver replay and every report): macros that start with the same inputs share those frames (`MacroTree`: 184 instead of 264 simulated frames per expansion); a node's rank and de-duplication key are computed once on the expanding thread, a bucket is ranked by index (nodes boxed), and the ~1500 nodes cut from a bucket are freed on the expanding threads; `Game::world_hash` hashes the entities a word at a time (`hash::WordHash`, ~5× faster; it is only compared within a run); `clean_route` trials start at the hold and stop at the first differing position.
  - **Auto-scroll levels** (M5, E26, D-075): the frame budget is 3× width px plus the frames the scroll takes to cross its zone (`solver::scroll_frames`: `(to − from) × 16 px / autoscroll_speed`, rounded up); ranking, actions and the window metric are the side level's. The scroll state is in `Game::world_hash`, so nodes that differ only in it (a later scroll start, a hold) are kept apart. The grey box `00_m5_autoscroll` is solved with no special handling (the D-075 fallback, route-limited zone jumps, was not needed).
  - **Climb levels** (M3, E14, D-054 + addendum D-059): nodes are ranked by `solver::search_progress` = x plus the height the feet gained above the player start's feet (subpixels); the frame budget is 3× (width + height) px; a shifted jump's recovery (fast path and re-planning) must also end with the feet at most 8 px lower than the original route's at the checkpoint, and the re-planning deadline is the checkpoint + 60 frames (side levels: + 30), since a missed plank costs one more jump up.
  - **Outputs**: `$CARGO_TARGET_DIR/reports/solver/<level>.{md,json}` (frames, search deaths, every jump with frame, x, hold, window, shift range and bounds; the narrowest; runtime), `preview/solver/<level>_narrowest.png` (state just before the narrowest jump's press) or `preview/solver/<level>_stuck.png` (furthest grounded state when it fails). `--write` writes `tests/replays/<level>_solver.replay` (`expect = complete frames=N..N deaths=0`, no shots; `--shots` adds `route_25/50/75`, which then need goldens after art-director approval).
  - **Verify step `solver`**: `cargo xtask solve --all`; fails if any level is not finished (the output names the stuck report and image), has no committed `tests/replays/<level>_solver.replay` (create it with `cargo xtask solve <level> --write`), or if that replay is **stale**: its inputs are not the fresh route (E35; the message gives both lengths and the first differing input; re-write it with `--write`, re-accept its goldens if it has shots, and say why in the commit). The step note lists the narrowest window per level; the output has a line `solver: N of M levels from the cache; searches …s, jump windows …s`. The step runs in two passes (D-082). **Pass 1**: every level's search (except cached ones), the only part with a clock, largest level (width × height) first, with the cores split between the levels searched at once and each search: about 7 threads per level, at most 8 (14 cores → 2 levels at a time with 7 threads each; ≤ 8 cores → one level at a time, as before E25), so never more busy threads than cores. **Pass 2**, after every search has ended: the route clean-ups (one level per core), then the jump windows of every level in one shared queue of shifts on all cores (no clock); then the reports in level order. Measured on 14 cores (E25): slowest search 16.5–18.2 s (St. Gilgen) in two runs under a machine load average of 20–35, ≥ 3.3× below the 60 s limit; 4 levels × 3 threads with windows overlapping the searches had given 21–25 s. Routes, windows and the output (in level order) do not depend on the thread split. A per-level `min_jump_window` in `[meta]` is in `backlog.md` (the meta table rejects unknown keys).

### L5 Replay regression tests (verify)
Replay files in `tests/replays/` contain the inputs per frame (run-length encoded) and expectations:

```
level    = salzburg
seed     = 1
source   = solver           # or: human (recorded in VNC)
expect   = complete frames=2400..3600 oblaten>=30 deaths=0
shots    = 120:intro 900:getreidegasse 2000:fiaker
---
R 60
RJ 18
R 40
...
```

- Running a replay asserts the expected outcome.
- Fixed room cameras (M7, E49, D-104): in a level whose `camera_top` is its bottom clamp (Café Zauner and its grey boxes), every replay that plays it (its `level` or `route` header) must keep the camera's y there on every frame, in every mode (xtask test `fixed_room_cameras_never_move_vertically_in_any_replay`, part of `check`).
- Every replay runs twice and compares `state_hash()` → determinism. `cargo xtask replay --all` (the `replays` step) plays the replay files in parallel (each on its own thread, both runs of a replay on the same thread); the output stays in file order.
- Implemented (M0): `jnr_core::replay` parses/formats the format and checks expectations; `cargo xtask replay <file|name|--all> [--shots]` runs replays on the real content (level by `meta.id`). Supported expectations: `complete [frames=a..b]`, `deaths=N`, `deaths<=N`, `dies_at frames=a..b`, `player_x>=PX`, `state=<playing|dying|stage_clear|game_over|title|stage_intro|paused>`, `no_event=<Event>`, `event=<Event>` (happened at least once; M1, E3), and (M1) `oblaten>=N` (HUD counter at the end), `score>=N`, `lives=N`; an optional header `start = playing|title` picks the flow (default `playing`: in play at once, no intros or pause; `title`: the real game from its title screen, D-025); (M2, D-047) an optional header `route = <level id> …` gives the levels of the run (stage i = station i on the route map; default: the standard route when `level` is a station such as `salzburg`, else the level alone), `stage=<station id>` checks the station at the end and `state=route_map` the route map, so a replay can span stage changes (`tests/replays/flow_route_*.replay` on the test-only levels `route_a`/`route_b`); (M3, D-060) `power=<normal|big|hackl>` checks the power state at the end; (M5, E30) `swimming=<true|false>` whether she swims at the end (D-076); (M7, E46) `boss_hits=N` the level's Oberkellner's hits at the end (0..=3; fails in a level without one, D-106); (M7, E47) `state=ending` (any phase of the ending) and `cleared=<true|false>` (the session's „durchgespielt" mark, D-107); `complete` is the first touch of the Maibaum and `state=stage_clear` holds for the whole goal sequence, which ends on the title screen; anything else is a parse error "not supported yet". A replay without any `expect` fails in the runner ("no expectations"), and the `replays` step fails if `tests/replays/` has no replay files. Frame numbers are `Game::frame()` (frame 0 = before the first step), ranges are inclusive, and every replay runs to its last input before end-state expectations are checked (D-013).
- Later: the headless runner is also built for `wasm32-wasip1` and run with `wasmtime`, and its hash is compared to the native one → native/web determinism.
- Physics changes may break replays on purpose; then `cargo xtask solve` re-creates the solver replays, and the change must be explained in the commit message. Human-recorded replays (recorded in VNC with `jnr-app --record <file>`, which writes `source = human` and a derived `expect` line so the replay passes right away; recording stops with a warning at the replay limit of 216 000 frames, so every recording parses) are kept as "feel" references.

### L6 Golden screenshots (verify)
- The `shots` frames of each replay are rendered headlessly and compared **pixel-exactly** to `tests/golden/<replay>_<shot>.png` (`cargo xtask golden`; the `goldens` verify step). The replays with shots are played in parallel, the results compared in file order.
- On mismatch: `$CARGO_TARGET_DIR/reports/golden/<name>_{actual,expected,diff}.png` (diff: changed pixels red over the darkened expected image). A missing golden fails too and writes the actual; so does a file in `tests/golden/` that no current shot uses, and two shots with the same golden name (`a_b` + `c` vs `a` + `b_c`).
- Review images before accepting: `cargo xtask replay <file> --shots` → `$CARGO_TARGET_DIR/preview/replays/<replay>_<shot>.png` (+ `_x4` copy).
- `cargo xtask golden --accept <replay>_<shot>|<replay>|--all` re-renders the shots (deterministic, so identical to the reviewed previews) and writes them into `tests/golden/`; it refuses replays that fail their expectations or are not deterministic.
- Updating goldens: `cargo xtask golden --accept <name>` is allowed only after an `art-director` APPROVED verdict for that change, and the commit message must state it.

### Audio (L3 + L6; E56, D-117, D-119)
Nobody can listen, so every sound is checked as numbers and pictures (`xtask/src/audio/`; the analysis uses f64 there, never in `jnr-audio`).

- **Render** — `cargo xtask audio render <id>|<file.sfx>|--all` writes to `$CARGO_TARGET_DIR/preview/audio/`: `<id>.wav` (44.1 kHz mono 16 bit), `<id>.json` (stats: `frames`, `duration_ms`, `peak_dbfs`, `rms_dbfs` (unweighted), `clipped_samples`, `dc_offset_pct` (signed), `onset_ms` and `silent_tail_ms` (time before the first / after the last sample ≥ −40 dBFS), `spectral_centroid_hz` (magnitude-weighted over Hann-windowed 1024-point frames), `first_sample`, `last_sample`, and the golden fingerprint `pcm`), `<id>_wave.png` (min/max and RMS per column, red line = −1 dBFS ceiling, dotted green = the target peak band) and `<id>_spec.png` (40 Hz – 20.48 kHz on a log axis, 24 rows per octave, dotted lines at 100 Hz, 1 kHz, 10 kHz; black = −80 dB under a full-scale sine, yellow-white = 0 dB). Both images share the time axis: 1 ms per column up to 1 s (longer sounds: ⌈s⌉ ms per column), dotted lines every 50 ms (every second when a column is > 5 ms). `--all` also writes the reviewer overview `sheet_spectrograms.png` (per sound the waveform above the spectrogram, labelled, four per row, all at the same time scale; cells in `sheet_cells/`). A path ending in `.sfx` renders a file outside `audio/` (a draft, a fixture). An empty `audio/` is fine ("nothing to do").
- **Targets** — `audio/targets.toml` has one table per sound id: `class` (required: `loud`, `normal`, `soft`, `ambience`, `jingle`, from `docs/audio-design.md` section 3), optional `peak_dbfs` (the SFX table's peak, overrides the class), `duration_ms`, `centroid_hz = [lo, hi]`, and `placeholder = true` for a stand-in.
- **Lints** — `cargo xtask audio lint [id]` (`check` step `audio-lint`; every one is an error; thresholds are constants in `xtask/src/audio/lint.rs`; each has a failing and a passing fixture in `xtask/fixtures/audio/`, tested by `every_lint_has_a_failing_and_a_passing_fixture`):

  | Lint | Rule | Source |
  |---|---|---|
  | `clamp` | no sample clamped by the renderer | proposal, rendering rules |
  | `ceiling` | peak ≤ −1 dBFS | audio-design §3 (master) |
  | `peak` | peak within `peak_dbfs` ± 1 dB, else the class band: loud −7 … −5, normal −10 … −8, soft −17 … −13, ambience −27 … −23, jingle −20 … −6 dBFS | §3, §6 |
  | `rms` | jingles: RMS −19 … −15 dBFS (−17 ± 2) | §3 |
  | `dc` | \|DC offset\| < 0.5 % of full scale | §3 |
  | `onset` | first sample ≥ −40 dBFS within 10 ms | proposal (responsiveness) |
  | `tail` | ≤ 50 ms below −40 dBFS at the end | proposal |
  | `edges` | first and last sample within ±33 (−60 dBFS): starts and ends at zero, no click | §3 |
  | `length` | SFX classes 20 … 1500 ms; jingles 200 … 10 000 ms | proposal (jingle limit raised from 6 s for §5's 8 s `game_over`) |
  | `duration` | `duration_ms` ± 10 ms, if set | §9 |
  | `centroid` | spectral centroid inside `centroid_hz`, if set | §9 |

  Wiring (also errors): every sound has a target, every target a sound, ids are unique across `audio/`, `class = "jingle"` exactly for `audio/jingles/`. A source that does not parse is an error with `file:line:col`.
- **Goldens** — `tests/golden/audio.toml`, one line per id: `jump = { pcm = "fnv64:<16 hex>", frames = …, peak_dbfs = …, rms_dbfs = …, centroid_hz = … }` (`jnr_audio::Pcm::fnv64` of the render; the stats are only for the failure report). `cargo xtask audio golden` (`verify` step `audio-goldens`) renders every sound: every sound that is not a placeholder must have a matching line, a placeholder must have none, and a line without a sound fails. A failure writes the actual review set (`<id>.wav`, `.json`, `_wave.png`, `_spec.png`) and the stored line (`<id>_expected.toml`) to `$CARGO_TARGET_DIR/reports/audio-golden/` and names them; a hash change prints the old and new frames, peak, RMS and centroid. Only the hash is stored, so there is no expected WAV or spectrogram (render the old source from git for that).
- **Accepting** — `cargo xtask audio golden --accept <id>|--all` writes the current hashes (`--all`: every non-placeholder sound). It refuses placeholders and sounds that fail `audio lint`. Allowed only after a **game-designer APPROVED** verdict on the review set from `audio render` (D-117); the commit message states it. `cargo xtask audio golden --prune` only removes lines (sounds that are gone, placeholders) and needs no verdict. The `guard-golden.sh` hook blocks direct edits of `tests/golden/audio.toml` like those of the screenshots.

### L6b Cue logs (verify, MA)
- The sound cues of a replay (`jnr_audio::cues::Director`, pure) as text, one `frame cue` line each: `cargo xtask replay <file> --cue-log` prints them (frame 0 = the game's first frame). Example lines: `   954 jingle boss_intro`, `  1044 sfx boss_telegraph W7`, `  1500 sfx pause I9 -2`, `   991 duck on`.
- Goldens: `tests/golden/cues/<replay>.cues` (testbed_route, salzburg_tour, cafe_zauner_boss_win_normal, wolfgangsee_gelse_dive, flow_game_over, qa_flow_pause_stops_timer, qa_m7_time_up_in_fight, flow_m7_cafe_zauner_ending_skip, m4_enemies_axe_singer). `cargo xtask cues` (the `cue-logs` verify step, also the xtask test `every_cue_golden_matches`) compares them; a mismatch names the first differing line and writes the actual log to `$CARGO_TARGET_DIR/reports/cues/<replay>.cues`.
- `cargo xtask cues --accept <replay>` writes (or adds) one golden, `--accept --all` rewrites every existing one. No reviewer gate (D-121): they are text, and their diff is the review; the commit message says which logs changed and why.
- `cargo test` also pins the rules: every `Event` decided, every cue id in `docs/audio-design.md`, the voice policy, and `testbed_route`'s 7 `jump` cues on its 7 jump presses.

### L7 Visual review (per visual change)
- The `art-director` agent reviews contact sheets, filmstrips and replay screenshots with a fixed rubric (readability, palette, silhouette, light direction, scale consistency, tile seams, HUD clipping, German spelling, "is the joke visible?").
- `cargo xtask filmstrip <replay>` makes a contact sheet of every 30th frame of a replay, so motion problems (jitter, clipping into walls) can be seen in one image.

### L8 Live smoke test (verify, last step)
- `cargo xtask vnc-smoke` (the last `verify` step): needs an X server on `$DISPLAY` (default `:1`; fails with "no X server answers on DISPLAY=…" otherwise). It builds the native app (debug) and runs it with `--replay tests/replays/testbed_route.replay --scale 4 --exit-after <last shot + 1>` and one `--screenshot-at <frame>:<file>` per shot of that replay, with a 60 s timeout (killed on timeout).
  - The app must exit 0, and every framebuffer screenshot (`$CARGO_TARGET_DIR/preview/vnc_smoke/<shot>.png`) must be **pixel-identical** to the golden `tests/golden/testbed_route_<shot>.png`: the real window path (replay input, fixed-step loop) produces exactly what the goldens show. On a mismatch `$CARGO_TARGET_DIR/reports/vnc-smoke/<name>_{actual,expected,diff}.png`; the app's output is in `preview/vnc_smoke/app.log`.
  - Audio (E54, D-118): the app also gets `--test-tone`, and its log must not contain quad-snd's `Audio thread died`. If PulseAudio is installed, xtask (`xtask/src/pulse.rs`) reuses a running daemon or starts one (`pulseaudio --daemonize=yes --exit-idle-time=-1 -n --load=module-native-protocol-unix`; it keeps running for later runs; a failed start counts only if no daemon answers within 5 s, since a parallel run may have started it), loads a null sink of its own, `jnr_null_<pid>` (unloaded afterwards; the daemon's default sink is untouched), gives it to the app as `PULSE_SINK`, records `<sink>.monitor` with `parec --latency-msec=50` (raw mono s16, 44.1 kHz, `preview/vnc_smoke/audio.s16`) while the app runs, and requires peak ≥ 1000 and no full-scale samples (measured: peak 3000 = 6000 × volume 0.5). Without Pulse (not installed, or `JNR_PULSE=off` with no daemon running; stop one with `pulseaudio --kill`) the step passes and the summary says `audio not exercised (<why>)`; the app then logs `audio unavailable (Can't open PCM device.)` once. E59 replaces the tone with real SFX onsets.
  - No-device run (always, with or without Pulse): a second, short app run (`--level testbed --test-tone --exit-after 60`, env `PULSE_SERVER=unix:/nonexistent`, so even a running daemon is out of reach and ALSA finds no device) must exit 0 and log exactly one `audio unavailable (` line, no `Audio thread died` and no `test tone played` (`preview/vnc_smoke/no_device.log`). Adds ~1.5 s.
  - It refuses to start while a window titled `Oblatenjagd` is already open ("close the running game first"). The 60 s timeout counts from the app's start, not including the build.
  - While it runs (after `xdotool search` finds the new visible `Oblatenjagd` window by title, since miniquad sets no `_NET_WM_PID`, plus 1.5 s), `import -window root` writes `$CARGO_TARGET_DIR/preview/vnc_smoke_root.png`. The screenshot is cropped to the window's geometry from `xwininfo` (`xdotool getwindowgeometry` counts the title bar twice), and at least 25 % of that area must be the palette sky colour `s` (±8 per channel: the desktop is 16-bit RGB565).
  - Takes about 13 s (the replay plays in real time).
- This checks the macroquad path (window, texture upload, scaling) that headless tests can't reach.
- `cargo xtask wasm-smoke` (part of `verify`, before `vnc-smoke`): builds the release wasm, serves `$CARGO_TARGET_DIR/web/` locally and loads it in headless Chromium with SwiftShader WebGL. It checks the DOM marker `<body data-wasm="loaded">` (module instantiated) and the 1280x720 screenshot `$CARGO_TARGET_DIR/preview/wasm_smoke.png` of the game's start, the **Salzburg title screen** (M1, E6): not blank, at least 25 % sky (palette `s` sky_light + `S` sky_blue together) and at least 5 % of the upper `S` band, which only the parallax sky has (a flat sky fill or the testbed fails). Measured: 36.4 % sky (20.4 % `s`, 16.0 % `S`; logo, rooftops, Festung and cobbles cover the rest), identical over repeated runs (the title backdrop is static; only the prompt blinks, which doesn't touch the sky).
  - **Frozen-frame check** (M2): the DOM run loads `smoke.html`, a copy of `index.html` that also loads a probe script (`xtask/src/wasm_smoke_probe.js`, never shipped). The probe wraps the game's per-frame export, drives it with a 60 Hz timer (headless Chromium runs `requestAnimationFrame` only a few times under a virtual-time budget, while timers and the game's clock follow virtual time), reads the title prompt's band (game rows 125–141) back with `gl.readPixels` after every frame and counts how often it changed (`data-smoke-prompt-changes`). At least 3 changes are required (one may come from the title appearing; the prompt blinks every 30 frames). Measured: 9 changes in 418 frames, identical over repeated runs; a game whose frame stops after 10 calls shows 1 and fails ("frozen frame"). Two `--screenshot` runs at different budgets were not usable: the blink phase at a given virtual time differs between runs.
- `vnc-smoke` stays on the testbed: it passes `--replay tests/replays/testbed_route.replay`, whose `level = testbed` overrides the app's default level (`salzburg`), and compares against the testbed goldens.

## Hooks (configured in `.claude/settings.json` in Milestone 0)

| Hook | Action |
|---|---|
| `PostToolUse` on Edit/Write of `*.rs` | `rustfmt` on that file |
| `Stop` | runs `cargo xtask check`; on failure it blocks the stop and returns the summary, so the agent must fix the problem first. Guarded with `stop_hook_active` to avoid endless loops. |
| `PreToolUse` on Edit/Write in `tests/golden/` | blocked; goldens change only through `cargo xtask golden --accept` (screenshots) and `cargo xtask audio golden --accept` (`audio.toml`) |

## Definition of done (per task)

1. `cargo xtask verify` is green.
2. New behaviour has a test (unit, game-feel, or replay).
3. Visual changes are APPROVED by `art-director`.
4. Code changes are reviewed by `code-reviewer` (architecture + determinism rules).
5. `docs/milestones.md` is updated; relevant docs and `docs/decisions.md` are updated.

## When agents are stuck

There is no human in the loop. Instead:
- After 3 failed rounds of the same fix or review, the orchestrator simplifies the task (smaller scope, simpler asset or mechanic), records the decision in `docs/decisions.md` and moves on. Deferred work goes into `docs/backlog.md`.
- Design questions are decided by the `game-designer` within the rules of `game-design.md` and recorded.
- Only permissively licensed dependencies (MIT, Apache-2.0, BSD, Zlib, CC0, CC-BY with attribution in `assets/LICENSES.md`). Anything else is not used.
- The only reasons to stop and wait for the human: something needs credentials, payment, or would delete/rewrite git history on `main`.
